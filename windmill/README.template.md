# Windmill

This directory's `f/{{folder}}/` and this README are generated by `meeting-kit render` from the kit's templates and
this repository's `meeting-kit.yaml`. Do not edit them by hand: change `meeting-kit.yaml` (or upgrade the kit), run
`meeting-kit render`, and commit the result. `meeting-kit render --check` fails when the committed tree differs from
what the config and the kit render, so the repository's checks catch a hand edit or a forgotten render. A kit
upgrade that changes the templates shows up here as a reviewable diff.

The tree is the meeting agents' schedules and flows, as Windmill content for one workspace folder, `f/{{folder}}/`.
The host keeps a checkout of this repository and pushes `f/{{folder}}/` from it. Each agent run uses the runner, the
agents and their instructions from that checkout, so a change merged to `main` reaches the next run after the
checkout's next pull.

## The host contract

The Windmill host relies on this repository for the tree, and this repository relies on the host for exactly this:

- **A checkout, not a flake input.** A flake input would copy the whole repository, transcripts included, into the
  world-readable Nix store. The host keeps a pull-only checkout of `main` instead, fast-forward only, and never
  writes to it. Never evaluate the checkout itself (`nix build <checkout>#…`, `nix run .#…`, `nix develop`, a
  `git+file:` reference): that copies the whole repository into the store too.
- **The tools, built after each pull** into the checkout's gitignored `.local/tools`, from the repository's tools
  package: `bin/meeting-kit` (the runner, with its own bun), `bin/nb-index`, `bin/check-kb` and `bin/check-tasks`.
- **Two read-only mounts in the `agent` worker** (`tag: agent`): the checkout at `{{mount}}`, and `/nix/store`,
  which the tools link into. A persistent volume at `/agent-home` keeps the `claude` install between jobs; this
  repository's claude config lives in `/agent-home/{{claude_config_dir}}`.
- **Its `f/infra/alert` script** (name, summary, description, severity, labels), which the flows call to send a
  `MeetingAgentNotice`, and alerting on failed `f/` jobs.
- **Windmill variables under `f/{{folder}}/`** (secrets, set on the host, never in this repository):

  | Variable | What it is |
  |---|---|
  | `repo_deploy_key` | An SSH key that can clone and push this repository |
  | `known_hosts` | The git server's host key line(s), for that SSH connection |
  | `repo_url` | The SSH URL the runner clones and pushes |
  | `claude_oauth_token` | The Claude account's `claude setup-token` |
  | `{{api_key_variable}}` | The MCP servers' API key, sent as `{{api_key_header}}` |
  | `webhook_secret` | The push webhook's HMAC secret (only with `windmill.webhook` in `meeting-kit.yaml`) |

`agent/run.sh` fails at once, before it reads any secret, if `{{mount}}/meeting-kit.yaml` or any of the four tools
is missing.

| Path under `f/{{folder}}/` | What it is |
|---|---|
| `agent/run.sh` | The one agent runner: `meeting-kit run <agent>` on the `agent` worker (90-minute limit) |
| `meeting_synthesis/tick.flow/` + `tick.schedule.yaml` | Runs on `windmill.schedules.synthesis`: `meeting-synthesis`, then a `notify` step for its notices |
| `meeting_synthesis/on_push.flow/` + `on_push.http_trigger.yaml` + `webhook_auth.resource.yaml` | Only with `windmill.webhook`: a signed push webhook that runs the tick when a push adds or changes a transcript |
| `workday_start.flow/` + `workday_start.schedule.yaml` | Runs on `windmill.schedules.workdayStart`: calendar gate, `meeting-triage`, one `meeting-briefing` per chosen meeting, then `check` |
| `meeting_briefing/calendar.ts` | The calendar gate's rule; its `Day` is meeting-triage's input |
| `shared/mcp.ts`, `shared/windmill.ts` | A minimal MCP client, and the Windmill variables API, for the Bun steps (no npm dependencies) |
| `shared/review.ts` | What the flows make of the runner's results: failures, notices, the alert |
| `shared/push.ts` | Only with `windmill.webhook`: which pushes are worth a synthesis run |

## What a run does

`agent/run.sh` reads its `f/{{folder}}/` variables, then drops every `WM_*` variable and keeps `claude` current on
`/agent-home`. It writes an MCP config naming every server in `meeting-kit.yaml` `mcp.servers`, whose header holds
`${{{api_key_env}}}` as a reference only, and runs `{{mount}}/.local/tools/bin/meeting-kit run <agent>` with
`MEETING_KIT_REMOTE`, `MEETING_KIT_TOOLS`, `GIT_SSH_COMMAND`, `TZ` (`{{timezone}}`) and `CLAUDE_CONFIG_DIR` set. The
runner makes its own clone of the repository, then runs `prepare`, the model, the scope checks, `finish`, the index
and checks (from `MEETING_KIT_TOOLS`, since the worker has no Nix), the commit (as `meeting-kit.yaml` `identity`)
and the push. The runner's JSON summary becomes the job's result (`status`, `created`, `cost`, `output`, `notices`),
with `commit` (the checkout's), `claude` and `wm_labels` added.

There is no synthesis gate: the runner's `prepare` finds the pending transcripts (a transcript without a
synthesis) and returns "nothing to do" before any model call, and the flow then shows as skipped. Every tick is a
full run, and a missed tick is covered by the next one.

## Push-triggered synthesis

With `windmill.webhook` set, `on_push.http_trigger.yaml` serves `POST /api/r/<windmill.webhook.route>` (not
workspaced, asynchronous). Windmill checks the request's HMAC-SHA256 signature (hex, in the header
`windmill.webhook.signatureHeader`) against the variable `f/{{folder}}/webhook_secret`, through the
`webhook_auth` resource. Point the git server's push webhook at that URL, with the same secret and a JSON body. The
`filter` step runs the tick only for a push to the default branch that adds or modifies a dated transcript
(`notebook/raw/meetings/YYYY-MM/YYYY-MM-DD-<slug>.md`); a payload without commit file lists runs it anyway, and a
deletion never does. The schedule stays as the backstop.

The host's sync has to push this folder's triggers and resources (a sync that skips them leaves the webhook
unserved), and the `webhook_secret` variable has to exist before the resource that names it is used.

## How the owner hears about it

- **A failed run** exits non-zero (the runner exits 1 and the job log's last line says why). The flow fails, and the
  host's failed-job alerting picks it up. In `workday_start`, every step before `check` carries on after an error,
  so all briefings get their chance; `check` then fails the flow once and names each failure.
- **A notice** from a run that succeeded, such as a recording judged not a work meeting, becomes one
  `MeetingAgentNotice` per flow run through `f/infra/alert`. The alert is labelled with the flow and the job, so two
  runs' notices never merge. If the alert can't be sent, the flow fails instead, with the notice in the error.

## Changing it

- **The runner, the agents, their instructions, `meeting-kit.yaml` `owner`/`identity`/`instructions`:** merge to
  `main`. The next run after the checkout's next pull uses them.
- **Timezone, calendar, MCP servers, schedules, folder, mount, webhook:** edit `meeting-kit.yaml`, run
  `meeting-kit render`, commit, merge. The host pushes the folder from the checkout. Never `wmill sync push` by hand.
- **A schedule, flow or script itself:** change the kit's templates (the kit's `windmill/` directory), then
  upgrade the kit here and render.
- **Try a run:** run `f/{{folder}}/agent/run` from the Windmill UI with `dry_run: 'true'`. It prints the prompt and
  the claude arguments, calls no model and pushes nothing. Both scheduled flows also take `dry_run`.
- Windmill applies no flow defaults to a scheduled run, so each schedule passes every flow argument; the kit's tests
  check this.
